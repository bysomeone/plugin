# RGB 桥系统设计

本文描述 chain33 上 `rgbx` 跨链桥（XBTC / RGB20）的架构、资金流、安全机制与失败模型，供架构评审、
安全审计与后续开发者使用。配置项见
[CONFIG.md](../../plugin/dapp/lightclient/rpc/lightclient/neutrino/CONFIG.md)，部署与值守见《02-运维手册.md》，
接口见《03-前端对接.md》。

> 本文描述的是**当前代码**的形态。gateway 之前架构（TSS 地址 + OP_RETURN 备注）的旧文档已删除；
> 若在历史提交或外部材料里看到那种充值流程，以本文为准。

## 1. 目标与非目标

目标：

- 用户在 chain33 主链上持有 `XBTC`（BTC 映射）或 `RGB20` 资产；桥负责 BTC ↔ chain33 的双向搬运。
- 桥的私钥由 TSS 门限组持有（CGGMP），任何单节点无法签名。
- 桥不暴露入站接口；所有对外入口收敛到网关。
- 资金的每一次移动都能在链上或审计账本里找到依据。

非目标：

- 不做通用跨链消息桥，只搬运已登记资产。
- 不托管用户私钥；用户签名只用于绑定充值请求。
- 不做链下撮合/流动性池。

## 2. 信任模型

| 角色 | 信任假设 | 能做什么 / 不能做什么 |
| --- | --- | --- |
| 用户 | 持有自己 chain33 地址的私钥 | 签名充值请求；发起提现；不能伪造他人请求 |
| 网关 | 可拒绝服务，**不可伪造** | 能延迟/丢弃请求；签名与金额在链上复核，篡改无效 |
| 桥节点（TSS 组） | 门限假设：少于 threshold 个节点作恶不丢资金 | 构造/签名 BTC 交易；不能单方面改收款地址或金额 |
| autonomy 治理 | 董事会按链上规则投票 | 调限额、暂停、手续费；不能直接动用户余额 |
| BTC 网络 | PoW / 最终性假设 | SPV 头链 + 确认深度决定何时可铸/可确认 |

三条硬边界：

1. **桥无入站端口**：生产只允许主动出站（网关 SSE/轮询、BTC RPC、链 RPC、节点间 libp2p）。
2. **网关不是权威**：它镜像 consignment 与审计事件，任何"网关说可以"都不构成链上依据。
3. **链上裁决**：铸造、销毁、限额、暂停都由共识状态判定；本地配置只能让节点"少做"，不能让它"多做"。

## 3. 组件

| 组件 | 职责 | 状态归属 |
| --- | --- | --- |
| `rgbx` 执行器（主链） | 跨链资产登记、充值铸造、提现锁定/确认销毁、治理配置与限额 | 共识状态 |
| `lightclient` 执行器 | BTC 头链校验与锚点、SPV 证明校验 | 共识状态 |
| 桥节点（neutrino） | 监听从链/主链事件、构造并签名 BTC 交易、投递 consignment | 本地钱包库 + 侧车 |
| RGB 侧车 | RGB 转账构建/校验/结算、合约精度、consignment | 侧车 `/data` |
| 网关 | 标准 RGB transport（consignment.post/get、ack）、签名充值请求、invoice、事件账本、运行指标聚合（`/metrics`） | 网关 data-dir（指标仅内存） |
| BTC 节点 | 提供区块/交易/广播；桥用 SPV 头链而非信任其 RPC 返回值 | 外部 |

## 4. 充值

### 4.1 RGB20：签名请求 → invoice → 铸造

```
用户 App ──签名请求──> 网关 ──SSE──> 桥 ──出票──> 网关 <──轮询── 用户 App
                                                        │
                                              支付 RGB invoice（标准 transport）
                                                        ▼
                                       桥拉取 consignment → 侧车结算 → 铸造交易
                                                        ▼
                                    chain33：验用户签名 + SPV + 合约身份 → mint
```

关键点：

- 请求包含 `request_id / chain33_addr / asset_symbol / amount / timestamp / pubkey / signature`。
  规范消息由 `depositrequest` 包定义，网关、桥、链上执行器**共用同一实现**。
- 链上铸造交易携带原始请求字段；执行器验证签名、地址与金额完全一致，并按 `request_id` 拒绝重放。
- 因此网关/桥即使被攻破，也只能拒绝服务，不能把资产铸给别的地址或改金额。
- 铸造前还要求：SPV 证明所在 BTC 区块达到链上 `minBtcConfirmations`；consignment 的 `asset_id`
  等于配置声明的合约；收款 seal 未铸过。

### 4.2 XBTC：链上充值地址 → 付 BTC

```
用户 ──RegisterDepositScript──> chain33（登记 userID → P2WSH 脚本）
官方节点 ──同步 watch 集──> 各签名节点
用户 ──付 BTC 到 P2WSH──> BTC 网络
桥 ──按脚本归因──> 等确认 → 提交带 SPV 的铸造 → 空闲时扫集回主池
```

- 充值地址 = `P2WSH(chain33 地址, TSS 群公钥)` 派生，链上按同一份派生认定归属，**无 OP_RETURN**。
- 地址只从链上登记读取（`GetDepositAddress`），桥不提供发地址的 HTTP 接口。
- 扫集把散落在用户 P2WSH 上的 BTC 归集回主池，否则桥"钱进得去、出不来"。
- 防双向领取：桥的任何自有付款（含扫集）都不得落回用户 P2WSH，否则同一笔 BTC 会被再认领一次。

## 5. 提现

### 5.1 生命周期

1. 用户在 chain33 提交 `Withdraw`：资产从用户余额转入**确定性的锁定地址**，并记不可变台账 + pending。
2. 桥轮询 pending，按资产类型进入 BTC 或 RGB20 结算路径。
3. 构造 → 交叉校验 → TSS 组签名 → 广播 → 把 consignment 投递给收款方 → 等 BTC 确认 → 提交 `Confirm`。
4. `Confirm` 校验 SPV + 确认深度 + 台账，从锁定地址 **Burn**，`burned` 累加。

### 5.2 锁定模型与解锁

- 锁定是单向的：资产离开用户余额后，正常出口只有"结算时 Burn"。没有超时自动退款。
- 解锁只允许在**尚未产生付款签名**时发生；授权来自 CGGMP 组对 `UnlockAsset` 的签名，链上验签后原额退回。
- 一旦签过付款，任何节点都拒绝为同一 burn 签解锁（签名集合必须相交）；此时只能继续结算。
- 人工放弃（abandon）与自动解锁共用同一解锁路径，区别只在触发者与本地状态记录。

### 5.3 RGB20 手续费

- 固定手续费读链上治理配置 `rgb20WithdrawFee`（按 symbol，最小单位），桥侧 TOML **没有**这个值。
- 判据：实际发给用户的资产必须精确等于 `链上 pending − 手续费`。发票没扣手续费会被拒绝，
  这笔提现停在锁定状态（资金已在链上锁定，桥不自动退款），走解锁路径处理。
- XBTC 没有固定手续费，矿工费从提现金额中按 BTC 交易大小扣除。

### 5.4 BTC 提现加价

只支持 BTC 提现：用户在链上提交 `BumpWithdrawFee`，桥用同一组 sticky 输入重签替换交易，新费率必须
比已生效费率高至少 1 sat/vB 且用户输出不低于 dust。RGB20 提现的 seal 绑在 BTC 交易输出上，替换会作废
整笔 RGB 转移，因此不支持。

## 6. 状态与存储

| 数据 | 位置 | 权威性 | 备注 |
| --- | --- | --- | --- |
| 跨链资产、铸造/销毁、限额、暂停、治理配置 | chain33 共识状态 | **权威** | 所有节点一致 |
| 提现锁定台账、pending 列表 | 共识状态 + LocalDB | 台账权威；pending 是节点私有索引 | 解锁判据不得依赖 LocalDB |
| TSS share、签名轮次记录 | 节点钱包库 | 节点私有 | 丢失需备份恢复 |
| btcwallet（地址管理器 + tx store + 生日） | 官方节点钱包库 | 节点私有 | 新钱包看不到历史充值（启动自检会告警） |
| RGB 账本、stock、合约声明 | 侧车 `/data` | 节点私有 | 链上查不回来，必须备份 |
| consignment、充值请求、事件账本 | 网关 data-dir | 镜像 | 不是权威；用于交付与审计 |

## 7. 安全机制清单

- **SPV 与锚点**：头链首块必须接创世/已知 checkpoint 或本地可回溯；执行器与中继共用同一份锚点表，
  不同 build 会表现为头链静默停滞。
- **确认深度**：链上 `minBtcConfirmations`（N）决定铸造/确认门槛；本地 `blockConfirmations`（B）是中继
  头链保留深度；大额充值可再加治理配置的额外确认数。中继门控 `best >= H + B + N - 1`。
- **资产身份**：RGB20 的 `asset_id` 必须等于配置声明；缺失即拒绝，不允许"配置缺失 ⇒ 校验失效"。
- **签名请求绑定**：request id、地址、资产、金额全部进入签名与链上校验；request id 链上一次性。
- **sticky seal / sticky 输入**：同一笔 burn 重试必须复用同一组 seal/UTXO，防止同一笔提现付两次。
- **反向领取防护**：桥的付款不得落回用户充值脚本；扫集输出只回主池。
- **限额与暂停**：单笔、1h/24h 滚动窗口、铸造窗口、大额延迟；治理暂停分充值/提现。
- **时间锁**：收紧类治理变更立即生效，放松类等约 24h；收紧提案会取消未生效的放松。
- **节点本地急停与自动熔断**：不依赖治理，只影响本节点；熔断不自恢复。
- **fail-closed**：配置缺失、精度未知、侧车不可用、头链不可用、签名节点核对失败，都拒绝动钱。

## 8. 失败分类

| 类别 | 例子 | 处理 |
| --- | --- | --- |
| 等待 | 确认数不足、头链落后、侧车未连上 | 下一轮重试，不动钱 |
| 可重试 | 链 RPC 抖动、网关 5xx、广播暂时失败 | 指数退避重试 |
| 确定性拒绝（本笔） | 合约身份不符、发票金额/手续费不符、签名节点拒签 | 停本笔；必要时走解锁 |
| 不可恢复（本笔） | 侧车资产已不存在、sticky 记录缺失、同一 burn 换 seal | 停本笔，人工介入；未签名可解锁 |
| 系统级 | 连续多笔 payout mismatch、TSS 组公钥不一致、头链锚点不符 | 熔断/拒启，人工排查 |

## 9. 审计事件账本

桥把链上不便聚合的事实投递到网关（at-least-once，本地 outbox 先落盘）：

- `deposit.settled / deposit.minted / deposit.rejected`
- `withdraw.locked / withdraw.broadcast / withdraw.consignment / withdraw.settled / withdraw.unlocked / withdraw.bumped`
- `sweep.completed`
- `treasury.snapshot`（预留，低频资金快照）

账本按 `(type, 主体)` 生成稳定 id，网关按 id 幂等、按游标读取、默认保留 90 天。它**不是权威账本**：
链上数据为准，事件用于出入金统计、对账与排障。

## 10. 测试与覆盖边界

E2E（`plugin/dapp/rgbx/cmd/ci/`）覆盖：充值地址链上绑定、RGB20 签名请求与铸造、正常提现、
并发提现、精度截断、永久拒签后的解锁、手续费负例、手工放弃、P2WSH 充值、扫集、冷备销毁还原、
网关事件账本、生日告警探针。

明确不覆盖：

- 生产规模与真实网络延迟；跨机恢复的属主/路径差异
- 主链深重组（只记录运营假设）
- RGB20 提现替换（不支持）
- 外部 RGB 合约（Tether USDT）上线前的真实合约行为
- 动态加节点（addshare）
