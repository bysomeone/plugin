# 备份与恢复

本文是备份/恢复的运维口径。备份范围的设计依据、代码证据与缺口清单见
[BACKUP_RECOVERY.md](../../plugin/dapp/lightclient/rpc/lightclient/neutrino/BACKUP_RECOVERY.md)；
脚本在
[scripts/](../../plugin/dapp/lightclient/rpc/lightclient/neutrino/scripts/)。

## 1. 备份范围

必须备份的状态只有四类，其余可从链或钱包重建：

| 源 | 内容 | 丢失后果 |
| --- | --- | --- |
| `main` datadir | 主链状态：`CrossChainInfo`、已铸供应量、充值/提现/操作台账 | **链状态与全部合约状态丢失**，只能整链重建 |
| `para1..4` datadir | authAccount 钱包、TSS share（`neutrino.db` 的 `rgbx-tss`）、lightclient 业务 bucket（含 `rgb20-receive` 的 consignment 原文）、`btcwallet.db` 及其生日 | 丢到剩余不足 `threshold=3` 份 ⇒ 旧地址下资金永久无法签名；丢 `btcwallet.db` ⇒ 历史充值永久看不见 |
| `para1..4` addrbook | libp2p 身份私钥 | 节点以"新成员"身份回归，旧组不认它 |
| 侧车 `/data` | `ledger.json`、`stock/`、`builds/`、`user_scripts.json` | RGB 是客户端验证，链上查不回来；合约认知与 seal 归属不可逆丢失 |

补充约束：

- `neutrino.db` 与 `btcwallet.db` 是**同一时刻**的两份状态，必须一起取样、一起还原。
- 侧车 `/data` 必须**成套**备份（`ledger.json` + `stock/` + `builds/` + `user_scripts.json`），
  单拿一份没有意义。
- `RGB_SIDECAR_CONTRACTS` 声明文件（JSON）**不在 `/data` 里**，用 `BACKUP_EXTRA_FILES` 单独纳入，否则丢失后
  连"重新 adopt 声明式合约"这条不完整的路也断了。若声明里用 `genesisConsignmentFile` 引用外部 genesis 文件，
  那个文件也要一并纳入。
- **网关数据有意排除**：网关不是权威账本，consignment 与充值请求可由用户按同一 `request_id` 重传/重取，
  事件账本只是审计镜像（链上数据仍在）。若审计要求事件连续，再把 `<gateway-data-dir>` 作为额外源加入，
  并在恢复后接受最多 90 天的历史窗口。

## 2. RPO / RTO、频率、保留与异地

| 项 | 要求 |
| --- | --- |
| RPO | ≤ 24 小时；每次大额操作前加做一次；DKG / refresh 落盘后立即一次 |
| RTO | 整组还原 ≤ 2 小时（不含链重同步与人工对账）；单节点 ≤ 30 分钟 |
| 备份频率 | 每日至少一次冷备；状态显著变化前加做 |
| 保留 | 日备 7 份、周备 4 份、月备 12 份 |
| 异地轮转 | 按 3-2-1 原则，**必须至少保留一份异地或离线副本**；实现方式（例如对象存储 + 客户端加密后上传）由运营方选择 |
| 备份新鲜度监控 | `check_backup_freshness.sh` + node_exporter textfile collector：> 24h P2、> 36h P1，见 §9 |

份额持有约束：`threshold=3` 时，**三份 share 不得同处一处**（三份即可签名）；每个 para 的运维方各自
持有自己的那份。

## 3. 冷备

冷备 = **停 → 打包 → 起**。停住写者是为了拿到一致样本，避免在线 `tar` 拼出撕裂的组合。

```bash
BACKUP_SOURCES=$'main=/var/lib/chain33/main\npara1=/var/lib/chain33/para1\nsidecar=/var/lib/rgb-sidecar/data' \
BACKUP_REQUIRED=$'main:mavltree\npara1:lightclient/neutrino.db\npara1:lightclient/btcwallet.db\npara1:addrbook/dht\nsidecar:ledger.json\nsidecar:stock' \
BACKUP_EXTRA_FILES=$'contracts=/etc/rgb/sidecar-contracts.json' \
BACKUP_OUT_DIR=/srv/backups \
BACKUP_STOP_CMD='systemctl stop chain33@main chain33@para1 rgb-sidecar' \
BACKUP_START_CMD='systemctl start chain33@main chain33@para1 rgb-sidecar' \
BACKUP_STOPPED_CHECK_CMD='! systemctl is-active --quiet chain33@main chain33@para1 rgb-sidecar' \
BACKUP_VERSION_CHAIN33="$(git -C /srv/src/chain33 describe --tags --always)" \
BACKUP_VERSION_SIDECAR="$(git -C /srv/src/plugin describe --tags --always)" \
  cold_backup.sh --tag "$(date -u +%Y%m%dT%H%M%SZ)"
```

要点：

- **`BACKUP_STOPPED_CHECK_CMD` 生产必设**：它断言"进程真的停了"。不给、又不用
  `--trust-caller-stopped` 显式认领，脚本会拒绝打包。`--trust-caller-stopped` 只用于 CI 这类
  "停服由调用方做且调用方已逐项核对"的场景。
- 失败路径会执行 `BACKUP_START_CMD`，避免把桥留在停着的状态。
- 包里带清单（每个文件的大小 + sha256）与来源版本；**成功产物只有
  `bridge-backup-<tag>.tar`**（同名的 `bridge-backup-<tag>/` 是打包期的临时目录，自检通过后删除；
  只有 `--keep-staging` 才会保留，见 §9 对新鲜度判断的影响）。
- 每个 para 都要有源条目。`[wallet] dbPath` 若不在 datadir 内，必须把钱包目录单独列成一个源
  （`--sources parawallet=...`），否则 authAccount 私钥不在备份集里。
- 脚本没有 `--dry-run`；只读预检用下一次恢复的 `--dry-run`（见 §4.1）完成。

## 4. 恢复

三种路径的能力差别很大，先选对：

| 模式 | 说明 |
| --- | --- |
| 整组还原（冷备 → 全量还原） | 按 §4.1，恢复到备份时刻的整组状态 |
| 单节点还原 | 用整组包 + `--only <label>` 只还原一个 para，其余节点不动（见 §4.2） |
| 整组从零 | 空机全量还原（share 完好）；share 全丢或链重建后的终局重建（见 §4.3） |

三条路径上线前都必须完成演练；其中整组从零、跨机器/跨属主场景必须在独立测试环境验证（见 §4.3、§7）。

### 4.1 整组还原

先只读校验，**在动现场之前**证明包与参数都可接受：

```bash
restore_backup.sh --dry-run --archive /srv/backups/bridge-backup-<tag>.tar \
  --target main=/var/lib/chain33/main \
  --target para1=/var/lib/chain33/para1 \
  --target sidecar=/var/lib/rgb-sidecar/data
```

再执行还原（脚本顺序：**停 → 校验包 → 落盘 → 复核 → 起**，坏包不会先毁现场）：

```bash
RESTORE_ARCHIVE=/srv/backups/bridge-backup-<tag>.tar \
RESTORE_TARGETS=$'main=/var/lib/chain33/main\npara1=/var/lib/chain33/para1\nsidecar=/var/lib/rgb-sidecar/data' \
RESTORE_EXTRA_TARGETS=$'contracts=/etc/rgb/sidecar-contracts.json' \
RESTORE_STOP_CMD='systemctl stop chain33@main chain33@para1 rgb-sidecar' \
RESTORE_START_CMD='systemctl start chain33@main chain33@para1 rgb-sidecar' \
RESTORE_STOPPED_CHECK_CMD='! systemctl is-active --quiet chain33@main chain33@para1 rgb-sidecar' \
RESTORE_REPLACE=move-aside \
  restore_backup.sh
```

要点：

- `--dry-run` 是只读的完整校验：解析参数 → 读包 → 逐文件核对 → 必需成员在位 → 将要落盘的每个
  label 都有目标（不给 `--only` 时就是全部 label）。
- `RESTORE_STOPPED_CHECK_CMD` 生产必设，语义与冷备侧相同。
- `RESTORE_REPLACE`：`refuse`（默认，目标非空即失败）、`move-aside`（整体改名为
  `<path>.pre-restore-<tag>`，可回滚）、`clear`（清空，CI 演练用）。
- 还原后脚本会逐文件复核 size + sha256。
- 演练验收标准：包自校验通过、真实销毁后还原、状态逐项相等（余额、侧车账本指纹、TSS peer 名单、
  钱包身份），且还原后跑通一笔提现。
- 单节点还原另见 §4.2（整组包 + `--only <label>`）。
- 演练的金额口径：必须按还原后的实际余额选金额，不能用默认值（默认值会表现为
  `insufficient USDT` / `ErrInsufficientBalance`，看起来像还原失败）。

### 4.2 单节点恢复（目标 ≤ 30 分钟）

前提：链上 `CrossChainInfo` 已存在（该组已 commit DKG）。此时**绝不允许 re-DKG**。

**不需要单独做单 label 包**：用整组包 + `--only <label>`。脚本仍然**完整校验整包**（manifest、
逐文件 sha256、必需成员），但只把选中的 label 落盘；未选中的 label 不需要 `--target`，也**不会**
被写入。`extra/<label>` 同理：只有该 label 被选中时才需要 `RESTORE_EXTRA_TARGETS`。点名的 label
不在包里、或给了 `--only` 但一个都不匹配，脚本直接失败（不会"看起来恢复成功"）。人工
`tar -xzf <包>/<package>/<label>.tar.gz` 再按 `manifest.tsv` 逐文件核对那条老路径不再需要。

| 步 | 动作 | 命令 / 判据 | 验收标准 |
| --- | --- | --- | --- |
| 0 | 造/选包 | 用 §9 确认**这次停机窗口内**有成功备份（整组包即可，不必是单 label 包）；`--dry-run` 会打印包里的 `TSS generation` | 包内 `tss.generation` 与链上同代 |
| 1 | 只读预检 | `restore_backup.sh --dry-run --archive <整组包> --only para1 --target para1=/var/lib/chain33/para1`；整包仍逐文件校验 | `--dry-run` 退出码 `0`，整包逐文件校验通过 |
| 2 | 停该节点 | 只停 para1，**不动其他节点**：`RESTORE_STOP_CMD='systemctl stop chain33@para1'`、`RESTORE_STOPPED_CHECK_CMD='! systemctl is-active --quiet chain33@para1'` | `RESTORE_STOPPED_CHECK_CMD` 通过；其他节点仍在运行 |
| 3 | 落盘 | `--only para1 --target para1=/var/lib/chain33/para1`（其余 label 不给 target 也能跑）、`RESTORE_REPLACE=move-aside`（现有目录改名为 `<path>.pre-restore-<tag>`，可回滚）、`RESTORE_START_CMD='systemctl start chain33@para1'`；展开后脚本会逐文件复核 size + sha256 | 退出码 `0`，逐文件 size + sha256 复核通过 |
| 4 | 起节点看日志 | `ensureDKG load from local db` = share 载入成功；无 panic = 与链同代；`ensureRefresh refresh round done` 表示补跑完成 | 三个日志信号都符合预期，无 panic |
| 5 | refresh 协调 | 若包的 refresh 记录与其余节点不一致（manifest 的 `tss.<label>.refreshRecord`），先按 [CONFIG.md](../../plugin/dapp/lightclient/rpc/lightclient/neutrino/CONFIG.md) §4.3.2 协调：refresh 是多方协议，**不要只起这一台让它单独发起一轮** | 包内 refresh 记录与其余节点一致，或全员协调后补跑完成 |
| 6 | 验签 | 该节点参与一笔真实签名（测试链用 E2E 场景） | 签名成功且链上验签通过 |
| 7 | 收尾 | §5 的 refresh / 对账 / 重新冷备；核对用时是否落在 ≤ 30 分钟的目标内 | §5 各项完成；用时 ≤ 30 分钟 |

**E2E 自动演练覆盖的断言**（`scenario_single_node_restore`，每轮 E2E 在整组场景之后跑，可用
`RGBX_BACKUP_DRILL=0` 一并跳过）：只备份、只销毁、只还原 para2（validator，避免扰动官方节点的
充值/钱包路径），断言

1. TSS peer 名单与还原前**完全一致** —— libp2p 身份私钥随包回来，节点不是"新成员"（B5）；
2. 钱包身份在位 —— authAccount 私钥（para 共识签名钥 + TSS 提交钥）是还原回来的，不是后续导入兜住的；
3. 节点追平主链后能参与一笔真实提现 —— TSS 签名 → 侧车 BuildWithdrawal → BTC 广播 → 链上销毁。

**自动演练的边界**：跨机器/跨属主（演练同机同用户）、启动日志行（如 `ensureDKG load from local db`）
的断言、refresh 协调步骤、≤ 30 分钟用时统计都不在自动演练内，必须在上线前于目标拓扑上单独验证。
金额口径同 §4.1：必须按当时的实际余额选，不能用默认值。

### 4.3 全组从零

分两种情形，**不要混为一谈**：数据没了但 share 备份还在（4.3.1，可还原），与 share 全丢 / 链重建
（4.3.2，只能重建且旧资产作废）。

#### 4.3.1 空机全组还原（share 完好，目标 ≤ 2 小时）

前提：整组最新成功备份可用、包内 `tss.generation.distinct=1`（几份 share 同代；不等于 1 时
`restore_backup.sh` 会告警，不要照用）。新机只装程序与配置，数据目录留空。

| 步 | 动作 | 命令 / 判据 | 验收标准 |
| --- | --- | --- | --- |
| 0 | 新机准备 | 每个 label 一个空目录；systemd 单元与配置就位（备份不包含可执行文件与配置） | 每个 label 的目标目录为空，服务已配置但未启动 |
| 1 | 选包 | §9 判 PASS；核对包名/时间与 `tss.generation`（`restore_backup.sh` 启动日志会打印） | §9 判 PASS，且包内 `tss.generation.distinct=1` |
| 2 | 只读预检 | `restore_backup.sh --dry-run --archive /srv/backups/bridge-backup-<tag>.tar`，为**每个** label 给 `--target`（`main`、`para1..4`、`sidecar`）；`--dry-run` 会读包、逐文件核对、核必需成员 | `--dry-run` 退出码 `0` |
| 3 | 确认无写者 | 新机上服务未起：设 `RESTORE_STOP_CMD='systemctl stop ...'`（未运行即无操作）与 `RESTORE_STOPPED_CHECK_CMD='! systemctl is-active --quiet ...'`，让脚本自己断言；也可手工 `systemctl is-active` / `ps` 核对后用 `--trust-caller-stopped`。**`--no-stop` 本身不是核对** | `RESTORE_STOPPED_CHECK_CMD` 通过 |
| 4 | 落盘 | 空目录用 `RESTORE_REPLACE=refuse`（非空即失败，最安全）；包里有 `extra/*` 时给 `RESTORE_EXTRA_TARGETS`，否则声明文件不会落回 | 退出码 `0`，逐文件 size + sha256 复核通过 |
| 5 | 起整组 | `RESTORE_START_CMD` 拉起 main + para1..4 + sidecar；逐节点看 `ensureDKG load from local db`、无 re-DKG panic、侧车 `RGB_SIDECAR_CONTRACTS: N contract(s) declared` | 各节点日志无 panic，侧车按声明数量完成 adopt |
| 6 | 验收 | 钱包生日告警不出现；链上 `opsupply-` 与侧车余额对账；TSS 组公钥与链上一致；跑一笔充值 + 一笔提现 | 对账一致、组公钥一致、充值提现各一笔成功 |
| 7 | 收尾 | §5 的 refresh / 对账 / 重新冷备；记录总用时（不含链重同步），与 ≤ 2 小时的目标比对 | §5 各项完成；总用时（不含链重同步）≤ 2 小时 |

多机部署注意：整组包可以**直接分发**到各台机器，每台只还原本机持有的 label：
`restore_backup.sh --only <label> --target <label>=...`（未选中的 label 不需要 target，也不会落盘）。
不必再按主机拆分单 label 包。跨机器/跨属主恢复时注意 tar 保留 uid/gid，属主不同时先 `chown`
（见 §8）；上线前必须在目标拓扑上完成一次跨机器演练。分发后也仍会由脚本按 `manifest.tsv` 逐文件核对。

#### 4.3.2 share 全丢 / 链重建（终局，不可当演练）

见 [BACKUP_RECOVERY.md](../../plugin/dapp/lightclient/rpc/lightclient/neutrino/BACKUP_RECOVERY.md) §3.3：
唯一出路是**整组 + 链一起重建**（新链上没有旧 `CrossChainInfo`）。**旧地址下的全部 BTC 与已铸
RGB20 作废**——这是"备份没做好"的终局，不是恢复方案。

- 处理顺序：先冻结业务与提现 → 上报并确认重建范围 → 新链重新 DKG、登记新地址 → 用户公告与对账。
- 侧车即使重新 adopt 合约，也只能得到"合约存在但余额为 0"的状态：历史 seals / receives / transfer
  不会回来。
- **不得在生产上演练**（演练即真实销毁旧资产）；只能在独立测试链上验证重建流程，该项演练必须在上线前完成。

## 5. 恢复后的收尾

1. **跑一轮 refresh**：删掉**所有**签名节点的 `cggmp-refresh-result` 记录后**一起重启**，节点会补跑
   一轮 refresh（只删一个没用，refresh 是多方协议）。完成后看日志 `ensureRefresh refresh round done`。
   理由与语义见
   [CONFIG.md](../../plugin/dapp/lightclient/rpc/lightclient/neutrino/CONFIG.md) §4.3.2：换材料、不换群公钥，
   地址与链上登记都不变。
2. **重新冷备**：refresh 之后旧包即"过代"（manifest 的 `tss.*` 与节点现状不符）。**备份变成过时而
   不重做，下一次恢复就会回到旧材料。**
3. **不要**让节点新建 `btcwallet.db`：新钱包看不到历史充值，启动自检会打印
   `ALERT wallet birthday cannot cover chain history`；此时应改用备份还原，而不是继续运行。
4. **对账**：链上 `opsupply-`（已铸总量）与侧车余额比对；确认 share 与链同代、事件账本游标可继续。
5. 启动自检清单见
   [BACKUP_RECOVERY.md](../../plugin/dapp/lightclient/rpc/lightclient/neutrino/BACKUP_RECOVERY.md) §3.4。

## 6. 旧备份与停机期间的数据

- **旧包的"回滚窗口"**：从备份时刻到故障时刻之间已经进链的记录（`CreateReceive`、consignment 映射等）
  会随还原消失。**BTC 付款本身不会消失**：完整的 `btcwallet.db` 会让钱包从备份时的 `SyncedTo` 向前回扫，
  重新发现这批付款（静态读码结论，**未实测**）。但"发现付款"不等于"入账"——链上侧要重新走一遍充值流程，
  用户需重传 consignment / 按同一 `request_id` 重新提交。包越旧，需要重传的窗口越大。
- **停机期间发生的付款**：桥停着时没有链上记录；恢复后由钱包扫描重新发现并正常入账（前提同样是
  `btcwallet.db` 生日覆盖历史）。若生日不覆盖，会走 `ALERT wallet birthday cannot cover chain history`
  而不是静默成功。
- **consignment 丢失**：协议是 at-least-once，钱包侧可重传；网关的 `deposit-requests/` 也可按同一
  `request_id` 重放出 invoice。不要让运维手工补账本。
- **主链回滚**：若 `main` 没有其它副本，它的回滚就是"链的回滚"。若只回滚 main 而不回滚 para，
  paracross 状态会不一致；这种情况下应先停整组，统一还原后再起。
- **网关数据不在备份范围**：恢复后接受用户重传 consignment、按 `request_id` 重新取 invoice；
  审计事件最多回溯 90 天。

## 7. 已知边界与要求

| 边界 | 技术事实 | 要求 / 验证方式 |
| --- | --- | --- |
| 钱包生日 | 备份只验存在与 sha256，**不能证明生日覆盖历史**；若 `btcwallet.db` 曾被误删重建，备份照常 PASS，但更早的充值永久不可见（启动只有 INFO 行与 ALERT） | 备份必须包含原始 `btcwallet.db`；恢复后确认不出现 `ALERT wallet birthday cannot cover chain history` |
| 单份 share 可用性 | 只验"与活文件一致"，**不证明该份额本身完好**；自检只比对组公钥，不校验 share 字段 | 必须通过整组还原演练间接验证份额可用；不得仅凭备份 PASS 认为份额完好 |
| Stock ↔ ledger 一致性 | 侧车 `stock/*.dat` 三份文件各自原子写入（tmp → `fsync` → `rename` → 目录 `fsync`），但文件之间不是事务；损坏或残缺的文件集会**拒绝启动**。备份侧没有一致性检查 | 必须停机冷备；启动自检会拒绝不一致的文件集 |
| 跨机 / 跨属主 | tar 按默认保留 uid/gid/mode；属主不同时先 `chown` | 上线前必须完成一次跨机器/跨属主恢复演练 |
| 异地留存 / 传输损坏 | 异地副本的完整性只能靠校验和与还原验证，冷备脚本不覆盖传输环节 | 异地副本必须至少验证一次可还原 |
| 备份或还原中途断电、网络分区 | 中断会留下半成品或撕裂的文件集；冷备脚本的 `BACKUP_STOPPED_CHECK_CMD` 与还原脚本的"先验包、后落盘"用于降低风险 | 上线前演练必须包含中断场景 |
| 备份年龄非 0 | 旧包会回滚备份时刻之后进链的记录（`CreateReceive`、consignment 映射等），BTC 付款本身不会消失（§6） | 上线前必须用非 0 年龄的包完成一次还原演练 |

## 8. 跨主机恢复的属主

解包按 tar 默认保留 uid/gid/mode。生产里 chain33 与侧车都以数据目录属主的身份运行；跨机器恢复且
属主不同时，**先 `chown` 再起进程**，否则会出现"文件都在但进程读不了"的假故障。路径可以不同——
恢复命令本来就按 `label=path` 指定目标，但每个 label 在目标机上只能落一个路径。

## 9. 备份新鲜度监控

脚本：[scripts/check_backup_freshness.sh](../../plugin/dapp/lightclient/rpc/lightclient/neutrino/scripts/check_backup_freshness.sh)。

**判据**（按 `cold_backup.sh` 的实际产物，不靠文件名猜时间）：

- 最新成功备份 = `BACKUP_OUT_DIR` 下 mtime 最新的 `<label>-backup-<tag>.tar`，且**没有**同名
  `<label>-backup-<tag>/` 临时目录、文件非空。
- 同名目录还在 ⇒ 正在打包/自检，或自检失败后的残留（半成品）⇒ 跳过，继续看上一份好包。
- 时间取 `.tar` 的 mtime（外层包写完的时刻；其后的自检可能再花数十秒到数分钟，GB 级数据更久，
  因此略早于"整次冷备真正结束"，对 36h 的阈值无影响）。
- ⚠️ `cold_backup.sh --keep-staging` 成功时也会留下同名目录，会被判成"未完成"；**生产保留的备份不要
  用它**。

用法：

```bash
# 只判断
BACKUP_OUT_DIR=/srv/backups check_backup_freshness.sh

# 同时写 node_exporter textfile（同目录临时文件 + mv，采集器不会读到半截）
BACKUP_OUT_DIR=/srv/backups BACKUP_MAX_AGE_HOURS=36 \
  check_backup_freshness.sh --textfile /var/lib/node_exporter/textfile/rgbx_backup.prom
```

stdout 固定一行：`PASS|FAIL ... latest=<包名> finished=<UTC> age=<年龄> threshold=<n>h`。
退出码：`0` 新鲜；`1` 过期或没有任何成功备份；`2` 参数错误（含 textfile 写失败）。

cron（每小时一次；分钟错开整点，避免与备份任务同分钟）：

```cron
17 * * * * root BACKUP_OUT_DIR=/srv/backups /opt/rgbx/scripts/check_backup_freshness.sh --textfile /var/lib/node_exporter/textfile/rgbx_backup.prom >> /var/log/rgbx-backup-freshness.log 2>&1
```

node_exporter 需启用 textfile collector（`--collector.textfile.directory=/var/lib/node_exporter/textfile`）。
写入的指标：

| 指标 | 含义 |
| --- | --- |
| `rgbx_backup_last_success_timestamp_seconds` | 最近一次成功冷备的时间（unix 秒）；没有成功备份时为 `0` |
| `rgbx_backup_age_seconds` | 距最近一次成功冷备的秒数；没有成功备份时为 `-1`（不是 `+Inf`） |

阈值与告警：**> 24h 记 P2；> 36h 或 `age = -1` 记 P1**。PromQL 建议用绝对时间而不是 age：
`time() - rgbx_backup_last_success_timestamp_seconds > 129600`——cron 停摆时 textfile 里的 age 会冻结在
旧值，而 timestamp 会随当前时间自然变大；无备份时 timestamp 为 `0`，同样会触发。告警规则见
[02-3-监控与告警.md](02-3-监控与告警.md) §6。

上线前必须把 cron 与 node_exporter textfile 接入，并实跑一次告警链路（覆盖新/旧/空/半成品/参数错误）。
它只回答"RPO 内有没有一次成功完成的冷备"；**不校验包内容**——包能不能读、清单对不对得上，仍由
`restore_backup.sh --dry-run` 证明。
