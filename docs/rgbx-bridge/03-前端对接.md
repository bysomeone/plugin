# RGB 桥前端对接文档

本文件面向钱包 / 前端开发者，说明如何调用充值、提现与查询接口，以及金额、手续费、确认数等口径。
产品与系统设计见同目录《01-系统设计.md》，节点与网关部署见《02-运维手册.md》。

> 所有金额字段（除特别注明）都是**该资产的最小单位整数**（int64）。展示给用户时按
> `chain33-cli rgbx getCrossChainInfo -s <SYMBOL>` 返回的 `precision` 换算；**不要**在前端硬编码
> 1e8，也不要用浮点做换算（float64 无法精确表示 `0.0006` 这类值，会少 1 个最小单位）。

## 1. 系统边界

| 组件 | 前端是否直连 | 说明 |
| --- | --- | --- |
| chain33 主链（rgbx 执行器） | 是（只读查询 + 发交易） | 查资产、充值地址、pending；提交 `RegisterDepositScript` 与 `Withdraw` 交易 |
| 网关（RGB HTTP JSON-RPC v0.2 + 充值请求） | 是 | 公开入口；提交签名充值请求、轮询 invoice；支付 invoice 也走同一网关 |
| 桥（neutrino / 侧车） | **否** | 桥不监听任何入站端口，全部由它主动连出 |
| autonomy 治理 | 只读 | 前端读取生效的桥配置（限额、暂停、手续费），不要手填 |

资产与链：

> **符号口径（最易混淆，务必区分）**：同一个跨链资产有两个拼写。
> - **原始符号**：`BTC`、`RGB20_USDT`。**查询、充值 / 提现动作、治理**都用它；链上记录也按它存储。
> - **映射符号**：`XBTC`、`XRGB20_USDT`（即 `X` + 原始符号）。**余额与转账**用它。
>
> 读路径（`getCrossChainInfo`、`get-bridge-config`、`get-effective-bridge-config`）两种拼写都接受：给出的拼写能精确命中就用它，
> 未命中再试另一种；但**提交交易**（`withdraw` 的 `-s`、治理提案）请用原始符号。前端展示余额时
> 仍按映射符号查（例如 `Chain33.GetBalance` 的 `asset_symbol`），不要拿映射符号去查链上记录。

- `XBTC`：桥在 BTC 上的映射资产，精度 8；充值付 BTC，提现收 BTC。
- `RGB20_USDT`（实际符号以链上登记为准）：RGB20 合约资产，精度以合约声明并经桥核对后写入
  `crossChainInfo.precision`；充值付 RGB 发票，提现收 RGB 发票。

## 2. 通用查询

```bash
# 跨链资产信息：precision / assetKind / tssAddress / pubkey（用原始符号）
chain33-cli rgbx getCrossChainInfo -s BTC
chain33-cli rgbx getCrossChainInfo -s RGB20_USDT

# 生效的桥配置（推荐）：全局记录与该资产记录合并后的限额、暂停、手续费
chain33-cli rgbx get-effective-bridge-config --asset-symbol RGB20_USDT

# 原始记录（排查用）：某一条治理记录本身，不做全局合并
chain33-cli rgbx get-bridge-config --asset-symbol RGB20_USDT
```

`get-effective-bridge-config` 是前端读取限额 / 暂停 / 手续费**唯一需要调用的查询**，返回字段：

| 字段 | 含义 |
| --- | --- |
| `assetSymbol` | 用于合并的资产符号；能解析到登记记录时是该资产登记的原始符号 |
| `configured` | 全局或该资产至少存在一条生效记录；`false` 表示从未配置（不限额、不暂停、不收费） |
| `config` | 合并后的生效值（字段含义见下表） |
| `pendingActivationHeight` | 尚未生效的**放松**（解暂停 / 提限额 / 降费）的激活高度；`0` 表示没有待生效变更 |
| `withdrawFeeMinUnits` | 该资产当前的 RGB20 固定提现手续费（最小单位）；`0` 表示未配置 |

`config` 的合并口径与执行器一致：

- `limitsEnabled` 是**数值限额总开关**（资产开关 + 全局主开关）。为 `false` 时下面的
  `maxPerTx` / `maxPerWindow1h` / `maxPerWindow24h` / `maxMintPerWindow` 仍会返回配置值，但**不生效**。
- `pauseDeposit` / `pauseWithdraw` 相互独立；全局记录或该资产记录任一暂停即生效。
- `withdrawMaxFeeRateSatPerVbyte`、`rgb20WithdrawFeeLockVbytes` 是全局共享值；资产记录未配置时由全局记录提供。
- `rgb20WithdrawFee` 是该资产的固定手续费表；直接读上面的 `withdrawFeeMinUnits` 即可，不必自己匹配符号。
- `get-bridge-config` 仍返回**原始记录**（单条、不做全局合并、无 `configured` / `pendingActivationHeight`），
  只在排查治理记录本身时使用；返回空记录表示该条记录从未配置。

`getCrossChainInfo` 返回字段（只列前端会用到的）：

| 字段 | 含义 |
| --- | --- |
| `assetSymbol` | chain33 侧资产符号 |
| `precision` | 小数位；`0` 表示桥尚未核对/回填，**此时禁止换算与展示金额** |
| `assetKind` | 资产类别（BTC / RGB20），不要用符号猜 |
| `tssAddress` | 桥在 BTC 的主池地址（扫集目标，前端一般不需要） |

## 3. 充值

### 3.1 RGB20：签名请求 → invoice → 付款

流程：

1. 前端生成 `request_id`（`[0-9A-Za-z_-]`，≤64 字节，建议 UUID 去掉连字符或带连字符均可）、
   `timestamp`（Unix 秒）。
2. 用**控制该 chain33 地址的私钥**对规范消息签名（见下）。
3. `POST <网关>/deposit/requests`。
4. 轮询 `GET <网关>/deposit/requests/{request_id}`，直到 `status=invoiced`（拿 invoice）。
5. 用支持 RGB HTTP JSON-RPC v0.2 transport 的钱包支付 `invoice`；桥结算后铸造到 `chain33_addr`。
6. 之后轮询 `GET <网关>/deposit/requests/{request_id}/status`，直到 `minted` 或 `rejected`（见下）。

规范签名消息（逐字节，UTF-8，`\n` 分隔，末尾**没有**额外换行）：

```
rgbx-deposit-request:v1
<chainTitle>
<request_id>
<chain33_addr>
<asset_symbol>
<amount>
<timestamp>
```

- 对上述字节做 `sha256`，用 secp256k1 私钥签**哈希**，输出 **DER** 编码签名（不是 compact/recoverable）。
- 提交的 `pubkey` 必须是 **33 字节压缩公钥**（hex）。
- 链上地址由该公钥按地址驱动推导，必须等于 `chain33_addr`；不一致直接拒绝。
- `chainTitle` 是链的 Title（网关与链上 `guardianParachainTitle` 一致），由部署方提供，前端不要自行猜测。

请求体：

```json
{
  "request_id": "dep-20261023-0001",
  "chain33_addr": "<chain33 地址>",
  "asset_symbol": "RGB20_USDT",
  "amount": 1000000,
  "timestamp": 1761177600,
  "pubkey": "<33 字节压缩公钥 hex>",
  "signature": "<DER 签名 hex>"
}
```

响应：

```json
{"request_id":"dep-20261023-0001","status":"pending","created":true}
```

`created=false` 表示同 id 的请求已存在（重试安全）；**同一 request_id 的首次内容为准**，不要用同一个 id
提交不同金额/地址。

轮询结果：

```json
{
  "request_id": "dep-20261023-0001",
  "chain33_addr": "...",
  "asset_symbol": "RGB20_USDT",
  "amount": 1000000,
  "timestamp": 1761177600,
  "status": "invoiced",
  "invoice": "<RGB invoice>",
  "receive_id": "...",
  "recipient_id": "..."
}
```

状态只有 `pending`（桥还没出票）与 `invoiced`（可以去付款）；铸造结果用下面的状态视图查询。

#### 状态视图（推荐查询铸造结果）

```http
GET <网关>/deposit/requests/{request_id}/status
```

```json
{
  "request_id": "dep-20261023-0001",
  "status": "minted",
  "chain33_addr": "...",
  "asset_symbol": "RGB20_USDT",
  "amount": 1000000,
  "timestamp": 1761177600,
  "invoice": "<RGB invoice>",
  "receive_id": "...",
  "recipient_id": "...",
  "btc_txid": "..."
}
```

| `status` | 含义 | 附带字段 |
| --- | --- | --- |
| `pending` | 网关已收请求，桥尚未出票 | — |
| `invoiced` | 已出票，等待付款 / 等待铸造 | `invoice`、`receive_id`、`recipient_id` |
| `minted` | 铸造交易已被链接受 | `btc_txid`、`amount` |
| `rejected` | 链上拒绝铸造（不会到账） | `reason`，已知时带 `btc_txid` |

口径与注意事项：

- 前两个状态来自网关的请求存储；`minted` / `rejected` 由网关从桥投递的审计事件账本
  （`deposit.minted` / `deposit.rejected`，按 payload 里的 `request_id` 匹配，取最新一条）派生。
- **`minted` / `rejected` 已给出终局，前端不必再靠轮询余额来判断**：`minted` 后余额增加，
  `rejected` 后应展示失败原因并提示用户联系运维，不要重复付款。
- 该状态视图是**便利视图**：账本只保留 `--events-retention`（默认 90 天），且事件投递是
  at-least-once；查询不到终局事件时状态可能停在 `invoiced`。**链上余额与
  `get-withdraw-status` 仍是权威**，对账、客诉与超期未决时以链上为准。
- 未知 `request_id` 返回 `404`；`GET /deposit/requests/{id}` 原样保留，字段与含义不变。

注意：

- `invoice` 里的金额**必须等于**请求里的 `amount`；桥在铸造时会再次核对用户签名，把收款地址与金额钉死。
- invoice 由桥生成，内含 transport 列表。只支持 v0.2 的钱包能直接付款；不支持时联系运维走别的交付方式。
- 充值到账延迟 ≈ 链上 `minBtcConfirmations`（默认 6 个 BTC 块，主网约 60 分钟）。
- 不要重复支付同一 invoice；如需多次充值，请每次使用新的 `request_id`。

### 3.2 XBTC：链上充值地址 → 付 BTC

1. 用户地址先注册（幂等，一个 chain33 地址只需一次）：

   ```bash
   chain33-cli rgbx register-deposit-script -k <用户私钥>   # 发交易
   ```

2. 读注册后的充值地址：

   ```bash
   chain33-cli rgbx get-deposit-address --user-id <chain33 地址>
   ```

   返回 `userID / address / pkScript / spec / height / index`。`address` 就是 P2WSH 充值地址，
   可以重复读取（同地址不变）。

3. 向 `address` 支付 BTC（普通 BTC 转账即可，不要向该地址发 RGB 资产）。
4. 桥按已登记脚本归因，等够确认数后自动铸造 `XBTC` 到该 chain33 地址；同时后台把 BTC 扫集回主池。

注意：

- 注册交易上链后，官方节点需要几秒把脚本并入 watch 集；刚注册就付款可能要多等一会儿才能被识别。
- 一个用户地址只有一个充值地址；不要用别人的地址付款。
- 充值确认数不足时不会铸造，资金安全停留在该 P2WSH 上，确认数够后自动继续。

## 4. 提现

### 4.1 提交

```bash
# RGB20：-d 是收款方 RGB invoice；金额是用户要"提出"的链上资产额
chain33-cli rgbx withdraw -a 0.001 -f 20 -d "<rgb invoice>" -s RGB20_USDT -k <用户私钥>

# BTC：-d 是 BTC 地址（-s 用原始符号 BTC）
chain33-cli rgbx withdraw -a 0.001 -f 20 -d "<btc address>" -s BTC -k <用户私钥>
```

- `-a` 是十进制字符串，精度从链上 `crossChainInfo.precision` 读取（前端不需要传精度）。
- `-s` 用**原始符号**（`BTC` / `RGB20_USDT`）；`XBTC` 这类映射符号只用于查余额 / 转账。
  `withdraw` 的精度解析两种拼写都能兜底，但交易里的 `assetSymbol` 会原样写入，统一用原始符号可避免
  同一资产出现两种动作符号。
- `-f` 是 BTC 手续费率（sat/vB），不是固定手续费。
- 提交成功后资产**立即从用户余额扣除并进入锁定地址**，桥随后构建、签名、广播并把 consignment
  投递给收款方。最终销毁发生在桥提交确认之后。

### 4.2 RGB20 手续费与发票金额（**最容易出错**）

RGB20 提现按资产收一笔固定手续费，值读链上治理配置：

```bash
chain33-cli rgbx get-effective-bridge-config --asset-symbol RGB20_USDT
# → withdrawFeeMinUnits: 1000
```

用户实际收到的资产必须**精确等于** `链上 pending 金额 − withdrawFeeMinUnits`。因此：

- 给桥的 RGB invoice 金额必须是 `amount − withdrawFeeMinUnits`，不是 `amount`。
- 发票不扣手续费会被桥拒绝（日志/错误里的措辞为 `payout mismatch`），这笔提现停在锁定状态，
  需要走解锁路径处理。前端应在开票前先读 `get-effective-bridge-config`，按上面公式开票。
- `withdrawFeeMinUnits` 为 `0` 或 `configured=false` 时，按 `1:1` 开票（`amount` 全额）。
- 该手续费是链上治理值，会随治理变化；**每次提现前重新读取**，不要缓存到本地配置文件。

### 4.3 查询进度

```bash
# 一次查询拿全：本地 pending 记录 + 共识终态 + consignment 哈希 + 派生状态
chain33-cli rgbx get-withdraw-status --tx-hash <提现交易哈希>

# 只查共识终态（settled / released；空 = 尚未终态）
chain33-cli rgbx get-withdraw-final-state --tx-hash <提现交易哈希>

# 某地址的全部 pending（含提现），升序分页
chain33-cli rgbx listPendingTxByFrom -f <用户地址>

# 单笔 pending（已知高度/索引时）
chain33-cli rgbx getPendingTx -h <高度> -i <索引>
```

`get-withdraw-status` 返回一个 JSON 对象：

| 字段 | 含义 |
| --- | --- |
| `pending` | 节点本地 pending 记录；节点没有该笔的本地索引时缺省（**不代表提现不存在**） |
| `finalState` | 共识终态：`settled` / `released`；尚未终态时为空 |
| `consignmentHash` | 确认交易登记的 consignment sha256（hex）；未登记为空 |
| `status` | 派生状态，见下表 |

| `status` | 含义 | 依据 |
| --- | --- | --- |
| `pending` | 已锁定，桥尚未结算 | 本地 pending 存在且共识无终态 |
| `settled` | 桥已付款、链上销毁完成 | 共识终态 `settled` |
| `released` | **已退款**：提现被取消，锁定资产已退回用户 | 共识终态 `released` |
| `unknown` | 无法判定（例如节点没有该笔的本地索引、哈希不对） | 既无终态也无本地 pending |

判定口径：

- **终态以共识状态为准**（`finalState` 由 Confirm / Unlock 写入链上状态），本地 pending 只是补充；
  两者不一致时以 `finalState` 为准。
- `released` **不是**"已付款"，而是"已退款/解锁"——前端必须显示为退款，不能显示为提现成功。
- `unknown` 不要当作失败或成功：先用 `chain33-cli tx query <tx-hash>` 等确认交易确实上链，再人工核对。
- 本地 pending 索引是节点私有的，且升级前写入的旧记录可能没有索引项，因此 `pending` 缺省并不罕见；
  这不影响终态判定。

`PendingTx` 关键字段：

| 字段 | 含义 |
| --- | --- |
| `txHash` | 用户的提现（锁定）交易哈希 |
| `amount` | 锁定的资产额（最小单位） |
| `feeRate` | 用户选择的 BTC 费率 |
| `confirmed` | 桥是否已提交确认并完成销毁（终态请以 `get-withdraw-status` 为准） |
| `targetAddress` | invoice 或 BTC 地址 |

前端展示直接使用 `get-withdraw-status.status`：提交成功 → `pending`（处理中）→ `settled`（已完成）或
`released`（已退款）。不要自己用 `confirmed`、日志或余额变化拼状态；用户余额在提交时就已扣除，不要重复扣减。

### 4.4 常见失败

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 提现交易被链拒绝 `withdraw amount does not cover ... fee` | 提现额不足以覆盖固定手续费 | 提高提现额 |
| 交易成功但一直不 `confirmed` | 桥校验失败（常见：发票金额没扣手续费） | 读桥日志找 `payout mismatch`；按解锁路径处理 |
| `insufficient BTC confirmations` | 桥尚未等到确认 / 头链落后 | 等待，不要重复提交 |
| 链上配置 `pauseWithdraw=true` | 治理暂停提现 | 提示用户暂停中 |
| 提现额超过限额 | 治理配置的单笔/窗口限额 | 降低金额或等窗口恢复 |

## 5. 金额、确认数与时间口径

- **精度**：唯一来源是 `crossChainInfo.precision`；`0` 表示尚未就绪，前端必须拒绝换算并提示"资产初始化中"。
- **充值确认**：RGB20 与 XBTC 都要求 BTC 付款达到链上 `minBtcConfirmations`（默认 6）；大额充值可能再
  加 `largeDepositExtraConfirmations`。
- **提现等待**：桥对主链 pending 使用 `mainChainConfirmations`（默认 6），给本链重组留回退窗口。
- **手续费口径**：RGB20 固定手续费是资产的最小单位整数；XBTC 的矿工费从提现额中扣除，实际到账略小于
  提交额（按 BTC 交易大小 × 费率估算）。

## 6. 联调检查清单

- [ ] 能读到 `crossChainInfo.precision != 0`，金额换算与链上余额一致（无 1e8 硬编码）。
- [ ] 充值请求签名可被网关接受；重复提交同一 request_id 返回 `created=false` 且金额不变。
- [ ] invoice 金额等于请求金额；支付后余额增加恰好等于请求金额。
- [ ] 充值结果读 `GET /deposit/requests/{id}/status`：`minted` 展示成功、`rejected` 展示原因；
  `invoiced` 超期未决时用链上余额复核。
- [ ] RGB20 提现前重新读取 `rgb20WithdrawFee`，发票金额 = 提现额 − 手续费。
- [ ] 提现提交后余额立即减少；`confirmed=true` 前不重复提交。
- [ ] 展示层不把 `pending` 当失败，也不在 `confirmed=true` 后重复扣款。
- [ ] 治理暂停（`pauseDeposit`/`pauseWithdraw`）时给出明确提示。

## 7. 接口边界（谁能调用什么）

| 接口 | 用途 | 调用方 | 鉴权 |
| --- | --- | --- | --- |
| `POST /deposit/requests`、`GET /deposit/requests/{id}`、`GET /deposit/requests/{id}/status` | 签名充值请求 / 查 invoice / 查铸造结果 | 前端、用户钱包 | 公开 |
| RGB HTTP JSON-RPC `/0.2/json-rpc` | 支付 invoice、consignment 交付 | 用户钱包 | 公开（协议内） |
| `GET /bridge/deposit/requests/stream`、`POST /bridge/deposit/invoices` | 桥拉取请求 / 回写 invoice | **桥** | bridge token |
| `POST /bridge/events` | 写入审计事件 | **桥** | bridge token |
| `GET /bridge/events?cursor=...` | 读取审计事件 | **审计/统计后端（前端平台的服务端）** | bridge token 或只读 events token |

`/bridge/*` 的 token **不得下发到浏览器或用户钱包**。审计/统计功能由前端平台的服务端调用网关，
token 只放在服务端环境变量里；建议给统计后端单独配置只读的 `--events-token`（见 §8）。

## 8. 审计 / 统计对接（服务端）

审计人员看到的数据由前端平台的服务端从网关事件账本拉取、落库后再展示。网关只提供 append-only
镜像，**链上数据仍是权威**；默认保留 90 天（`--events-retention`）。

### 8.1 鉴权

- 推荐给审计后端单独配置**只读 token**：网关 `--events-token`（环境变量 `RGB_GATEWAY_EVENTS_TOKEN`，
  ≥16 字符且必须与 `--bridge-token` 不同）。它只能 `GET`，`POST /bridge/events` 会返回 `403`。
- 未配置只读 token 时，只能用 bridge token 读（同时拥有写入权限，不建议交给统计侧）。
- 若网关启用了 mTLS（`--client-ca`），审计后端还必须提供客户端证书。
- 请求头：`Authorization: Bearer <token>`。

### 8.2 写入（桥调用，前端口径仅供理解）

```http
POST /bridge/events
Authorization: Bearer <bridge-token>
Content-Type: application/json

{"id":"withdraw.broadcast:3f2a...","type":"withdraw.broadcast","payload":{"chain33_tx_hash":"...","btc_txid":"..."}}
```

`id` 是幂等键：同 id 重复提交返回已存在的 `seq`，不会产生第二行。成功返回
`{"seq":N,"duplicate":false}`；`400` 为未知类型/缺 id/payload 非法；`401/403` 鉴权失败。

### 8.3 读取（审计后端调用）

```http
GET /bridge/events?cursor=<seq>&limit=<1..1000>
（等价路径：/bridge/events/query）
```

```json
{
  "events": [
    {"seq": 1, "id": "deposit.settled:...", "type": "deposit.settled",
     "occurred_at": 1761177600, "payload": {"receive_id": "...", "amount": 1000000}}
  ],
  "next_cursor": 1,
  "has_more": false
}
```

- `cursor` 为 0 或省略 = 从头读；返回 `seq > cursor` 的事件，按 seq 升序。
- `limit` 默认 200，最大 1000；`has_more=true` 表示还有下一批。
- `next_cursor` 直接作为下次请求的 `cursor`；清理过期事件后 seq 仍单调递增，游标不会失效。
- 投递是 at-least-once：可能看到重复 `id`（桥重启后重发），**按 `id` 去重**。
- 统计侧应持久化自己的游标，不要每次从 0 拉全量。

### 8.4 事件类型与 payload

| type | 触发点 | payload 关键字段 |
| --- | --- | --- |
| `deposit.settled` | 桥归因到一笔充值（侧车结算） | `receive_id`, `request_id`, `chain33_addr`, `asset_symbol`, `amount`, `btc_txid`, `vout` |
| `deposit.minted` | 铸造交易已被接受 | 同上 |
| `deposit.rejected` | 链上拒绝铸造 | 同上 + `reason` |
| `withdraw.locked` | 开始处理链上提现（资产已锁定） | `chain33_tx_hash`, `asset_symbol`, `amount`, `fee`, `expected_payout`, `fee_rate` |
| `withdraw.broadcast` | BTC 交易已广播 | 上述字段 + `btc_txid`, `recipient_seal`, `change_seal` |
| `withdraw.consignment` | consignment 已投递/登记 | `chain33_tx_hash`, `btc_txid`, `recipient_id`, `channel`（`transport`/`gateway`/`publish`） |
| `withdraw.settled` | 桥提交确认、链上销毁 | `chain33_tx_hash`, `btc_txid`, `confirm_tx_hash` |
| `withdraw.unlocked` | 解锁交易提交成功 | `chain33_tx_hash`, `asset_symbol`, `amount`, `owner` |
| `withdraw.bumped` | BTC 提现替换交易已生效 | `chain33_tx_hash`, `asset_symbol`, `amount`, `previous_fee_rate`, `requested_fee_rate`, `effective_fee_rate`, `bump_request_tx` |
| `sweep.completed` | 扫集交易已广播 | `sweep_txid`, `input_count`, `input_value`, `fee`, `fee_rate` |
| `treasury.snapshot` | 预留（低频资金快照） | 保留 |

金额字段都是最小单位整数，换算用 §1 的 `precision` 口径。`fee`/`expected_payout` 的单位与资产一致；
`sweep.completed` 的 `fee`、`input_value` 是 sat。

### 8.5 统计口径建议

- 入金总量：按 `asset_symbol` 聚合 `deposit.minted.amount`；用 `deposit.settled` 与 `withdraw.*` 对齐时间线。
- 出金总量：按 `withdraw.settled` 聚合；`withdraw.locked` 与 `withdraw.settled` 的差额即"处理中"。
- 退款：`withdraw.unlocked` 单独统计（原因在桥日志，事件里只有金额与 owner）。
- 桥收益：`withdraw.settled.amount − withdraw.broadcast.expected_payout` 的合计，对照 `withdraw.locked.fee`。
- 资金归集：`sweep.completed` 的 `input_count/input_value/fee`，用于估算主池补充节奏。
- 不要用事件账本计算供应量或余额：那两项以链上查询为准。
